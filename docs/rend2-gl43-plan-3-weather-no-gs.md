# План 3. Дождь и всплески без геометрических шейдеров

Относится к [rend2-gl43-review.md](rend2-gl43-review.md), строка «Weather: rain simulation, splashes». Объём:
средний (3–5 дней). **Шаг 0 решает, делать ли дальше.**

## Что сейчас

- **Симуляция:** transform feedback (`glsl/weatherUpdate.glsl`), по точке на каплю. До 5000 капель на чанк ×
  9 чанков = 45 000 точек на тип погоды (`tr_weather.cpp`, `particleCount`). Это остаётся как есть.
- **Струи:** `glsl/weather.glsl` рисует `GL_POINTS`. Геометрический шейдер (секция `/*[Geometry]*/`, строка
  152) делает из каждой точки квад (4 вершины), отбрасывает невидимые капли, считает освещение капли `RainLight`
  (сетка освещения, `u_RainLight`) и динамические источники (`weather_lighting.glsl`). Смешивание: для дождя
  аддитивное `ONE, ONE` (`tr_weather.cpp`, около строки 1935), для песка и режима премультипликации — over.
- **Всплески:** `glsl/weatherSplash.glsl` (`RB_AddRainSplashes`, `tr_weather.cpp` около строки 900) тоже рисует
  все 45 000 точек. GS (`max_vertices = 8`) почти для всех капель сразу делает `return`: живых всплесков обычно
  сотни. Смешивание премультиплицированное over. Статистика всплесков идёт через query
  `GL_PRIMITIVES_GENERATED` (`RB_RainSplashQuery`).

## Зачем

На Intel и AMD геометрические шейдеры медленные: у каждого вызова GS накладные расходы на выходной буфер, даже
когда он ничего не выдаёт. Всплески тратят 45 000 вызовов GS ради нескольких сотен квадов. Струи тратят GS на
каждую каплю, хотя квад можно построить в вершинном шейдере.

## Шаг 0. Замер (обязателен)

`r_speeds 100`, таймеры «Weather draw» и «Weather splashes» уже есть (`RB_DrawItems`, `tr_backend.cpp`).
Сильный дождь (`particleCount 5000`), Intel и NVIDIA, 1080p.
- **Если оба таймера < 0.2 мс на Intel — план не делать**, записать замер в обзор.
- Иначе продолжать.

## Как сделать

### A. Струи: квад строится в вершинном шейдере (работает и на GL 3.2)

- Рисовать `GL_TRIANGLES`, 6 вершин на каплю (`numVertices = particleCount · 6` на чанк). Капля
  `i = gl_VertexID / 6`, угол `gl_VertexID % 6`.
- Данные капли VS читает из того же VBO, в который пишет TF. Буфер привязан как buffer texture (RGB32F позиция,
  скорость; GL 3.1, работает и на 3.2) или как SSBO на GL 4.3. Атрибуты вершин больше не нужны.
- Перенести тело GS (строки 152–368 `weather.glsl`) в функцию VS `RainCorner(i, corner)`. Отбраковку
  (`var_Culled`, вне дистанции, под крышей) заменить на вырожденную вершину (`gl_Position = vec4(0, 0, 0, 1)` для
  всех 6 вершин капли — нулевая площадь, растеризации нет).
- **Проблема:** освещение капли (`RainLight` и динамические источники) в GS считалось 1 раз на каплю, в VS будет
  6 раз. Поэтому для GL 4.3 добавить compute-подготовку (пункт B). Для GL 3.2 оставить старый GS-путь, он
  остаётся эталоном.
- Порядок вершин тот же (по капле), так что blending over в песке не меняет результат.

### B. Compute-подготовка (GL 4.3)

Ядро `glsl/weather_prepare.glsl` после TF-обновления, по потоку на каплю:
1. **Видимость:** тот же предикат, что был в GS (дистанция, LOD `r_rainLOD`, «под крышей» по карте глубины
   погоды, отсечение по чанку).
2. **Для видимой:** освещение (сетка + динамические источники) один раз, запись в per-particle буфер:
   позиция, скорость, цвет `RGBA16F`.
3. **Всплески:** для капли с живым всплеском — запись её индекса в компактный список. Порядок в списке нужен
   детерминированный, иначе over-смешивание всплесков будет мерцать. Поэтому двухпроходное сжатие: счёт на
   рабочую группу, затем префикс по группам маленьким диспатчем, затем запись. Затем заполнить
   `DrawArraysIndirectCommand { count = 12 (2 квада), instanceCount = n }`.

Отрисовка:
- струи — инстансами по видимым (или все, с вырожденными) с чтением цвета из буфера;
- всплески — `glDrawArraysIndirect`, VS строит 2 квада по `gl_InstanceID` (номер в компактном списке).

**Инфраструктура:**
- загрузить `qglDrawArraysIndirect` в `GLimp_InitModernFunctions` (`tr_extensions.cpp`), `qgl.h`;
- новый `DRAW_COMMAND_ARRAYS_INDIRECT` в `DrawItem` и в `switch` `RB_DrawItems` (`tr_backend.cpp`), привязка
  `GL_DRAW_INDIRECT_BUFFER`;
- барьер `GL_COMMAND_BARRIER_BIT | GL_SHADER_STORAGE_BARRIER_BIT` после подготовки;
- статистику всплесков (`RB_RainSplashQuery`) заменить асинхронным чтением счётчика (как кольцо с fence у воды).

Варианты программ:
- `weatherSplashSurfaceShader` (ответ поверхности `r_rainSplashSurfaceResponse`) — тоже в VS-версию;
- снег/песок/пыль используют `weather.glsl` с `u_WeatherType` — тот же путь.

Переключатель `r_weatherCompute 1` (по умолчанию 0 до проверки, без рестарта); при 0 или GL 3.2 — GS-путь.

## Проверка

- **SDL-тест** (`tools/rend2/test_gl43_compute.py`): одинаковый набор капель, отрисовка GS и новым путём в
  float-таргет, разница ≤ 1e-4 для аддитивного дождя, ровно ноль для числа покрытых пикселей; для всплесков
  компактный список совпадает с множеством капель, для которых GS выдавал вершины.
- **В игре:** скриншоты при `r_weatherCompute 0/1` с `r_rainSplashDebug 1` (маркеры всплесков) и без; таймеры
  шага 0 до и после.

## Готово, когда

Таймеры «Weather draw» + «Weather splashes» на Intel заметно меньше (цель — в разы для всплесков), картинка
совпадает, статистика всплесков работает.

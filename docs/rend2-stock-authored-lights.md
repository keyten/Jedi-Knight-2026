# Источники света в стоковых BSP Jedi Academy

Проверено 10 ноября 2026 года на локальной Steam-установке, только официальные
`assets0–3.pk3`. В них 61 запись BSP: 57 различных карт, из которых 34 SP и 23 MP.
Четыре MP-карты заменены версиями из `assets3.pk3`; проверены также старые версии
из `assets0.pk3`. Модификации и loose overrides не участвовали.

## Что удалось извлечь

Из entities извлечены **52 настоящих авторских light entities**:

| Карта | Источников | Характер данных |
|---|---:|---|
| `t1_fatal` | 1 | `Hall_Firelight`, style 32 |
| `t3_bounty` | 47 | 13 групп по `targetname`, переключаемые огни |
| `t3_stamp` | 4 | Две группы `boom3`/`boom4`, по два источника |
| Остальные 54 карты | 0 | Включая все 23 MP-карты |

Все 52 имеют `targetname` и lightstyle. Они образуют 16 групп переключения;
19 источников имеют `spawnflags=4`, то есть START_OFF в игровом обработчике SP.
Отсутствие сохранённых обычных источников в других картах подтверждено прямым
разбором BSP и независимым экспортом через Q3Map2 2.5.17n-git-d9338309e.

Пример из `t1_fatal`, скопированный без изменения значений:

```text
{
"targetname" "Hall_Firelight"
"_color" "1 .72 .42"
"scale" "2"
"light" "250"
"origin" "115 -2420 4545"
"classname" "light"
"style" "32"
}
```

`light=250` и `scale=2` сохранены раздельно. Это параметры старого компилятора;
их нельзя объявлять канделами или напрямую подставлять как мощность современного
источника с гарантией совпадения изображения. Состояния переключения и lightstyle
нужно учитывать отдельно от положения/цвета/интенсивности.

## Что означает keeplights

В исследованном коде Q3Map2 `-keeplights` — параметр стадии BSP. Он сохраняет
`_keepLights=1` в worldspawn для следующих стадий. `SetLightStyles` удаляет
неименованные `light*`, если сохранение выключено, но оставляет источники с
`targetname`, нужные для переключаемых lightstyles. Это объясняет наблюдаемый
состав entities. См. первичный
[код SetLightStyles](https://github.com/Garux/netradiant-custom/blob/master/tools/quake3/q3map2/writebsp.cpp).
Локально также проверен ранее сохранённый NetRadiant `writebsp.c`, строки 357–398.

Утверждение, что большинство стоковых карт сохранило все light entities,
**для проверенной Jedi Academy не подтвердилось**. Сами оставшиеся 52 огня
не доказывают применение `-keeplights`: переключаемые источники сохраняются
и без этого режима. Добавление флага после компиляции или декомпиляция не вернёт
удалённые записи. Декомпилятор способен восстановить часть геометрии и прочитать
сохранившиеся entities; дополнительных исходных ламп в нём нет.

## NPC и количество игровых entities

В [G_GetLightLevel](../code/game/NPC_senses.cpp) вызывается `cgi_R_GetLighting`.
В [ванильном RE_GetLighting](../code/rd-vanilla/tr_light.cpp) используется
`R_SetupEntityLightingGrid`: ambient, directed и направление читаются из
запечённой lightgrid. Поэтому эта функция не требует сохранённых `light`
entities. В rend2 путь `RE_GetLighting` также использует lightgrid.

В [SP_light](../code/game/g_misc.cpp) источник без `targetname` немедленно
освобождается через `G_FreeEntity`. Именованный источник остаётся для управления
lightstyles и имеет `SVF_NOCLIENT`. Таким образом, фраза «движок игнорирует lights»
подходит к обычным статическим лампам, но не ко всем переключаемым источникам.
Нельзя из неё выводить, что любые сохранённые light entities вообще никогда
не занимают игровые слоты.

## Другие сохранившиеся сведения об освещении

Из оригинальных `.shader` и геометрии BSP дополнительно экспортированы:

- **3 606 фрагментов поверхностей** в 35 картах, шейдер которых явно содержит
  положительный `q3map_surfacelight`. Это 3 141 planar, 462 patch и 3 triangle
  soup. Для каждого сохранены материал, вершины, нормали, UV, индексы и номер
  inline model. Это количество фрагментов BSP, а не количество исходных ламп.
- **14 деклараций солнечного света** в используемых шейдерах. Три подавлены
  `_noshadersun=1` (`hoth2`, `t1_rail`, `mp/duel1`); ещё две имеют нулевую
  интенсивность (`mp/ctf2`, `yavin2`). Остаются девять положительных деклараций,
  не подавленных этим ключом. Это авторские параметры шейдера, а не доказательство
  неизменного применения этих параметров при исторической сборке карты.
- Полный worldspawn с `_minlight`, `_mingridlight`, `ambient`, `_color`,
  `gridsize` и прочими сохранившимися ключами.
- 16 156 glow-only фрагментов посчитаны отдельно: `glow` сам по себе не означает,
  что поверхность освещала окружение при компиляции.

Например, в `hoth3` обычных light entities нет, но сохранились пять фрагментов
`textures/impdetention/light_blue` с `q3map_surfacelight 2000`.
В `hoth2` найдено `sun 255 255 255 355 345 85` у `textures/skies/hoth`, однако
worldspawn содержит `_noshadersun=1`: использовать эту декларацию как доказанный
источник солнца для карты нельзя. Такое подавление учитывается в экспорте.

Для `q3map_surfacelight` не вычислялся цвет по текстуре и не воспроизводились
компиляторные subdivision, backsplash, bounce и другие операции. У 36 фрагментов
геометрия принадлежит inline models: для размещения в мире нужно учитывать
entities и их преобразования. Patch экспортирован как контрольная сетка Безье.
Светящиеся текстуры, FX и внешние модели не превращались автоматически в лампы.

## Файлы и воспроизведение

Результат находится в `build/stock-light-extraction/`:

- `lights.json` — все 52 источника с оригинальными key/value, координатами,
  цветом, `light`, `scale`, style, targetname и SHA-256 исходного BSP.
- `maps/<имя>/lights.ent` — исходные блоки только источников света.
- `maps/<имя>/entities.ent` — исходная секция entities побайтно, включая NUL.
- `maps/<имя>/lighting.json` — lights, worldspawn, солнечные декларации,
  исходные определения шейдеров и возможные targets.
- `maps/<имя>/surface-emitters.json` — геометрия surfacelight-фрагментов.
- `summary.json`, `report.md` — полный перечень карт и счётчики.
- `verification.json` — проверка всех 61 вариантов BSP через Q3Map2 `-exportents`.

Скрипты и команды: [tools/rend2/stock_lights](../tools/rend2/stock_lights/README.md).
Извлечённые игровые данные остаются в игнорируемом `build/`.

Проверка Q3Map2 совпала для всех 61 BSP с учётом только Windows CRLF и завершающих
NUL/перевода строки. Прямые экспорты entities всех 57 выбранных карт побайтно
совпали с исходными lumps. Наборы key/value в 52 light-блоках также совпали
с нативным экспортом. Шесть тестов проверяют повреждённые BSP/entities,
комментарии и строки, дубликаты ключей и разграничение glow/surfacelight/sun.

Практическое применение: эти 52 огня можно использовать как точные авторские
позиции и исходные параметры, а сохранившиеся surfacelight и sun — как отдельные
авторские сведения для relighting. Для остальных удалённых точечных и spot
источников всё ещё нужны исходные `.map`, ручная расстановка или реконструкция
по запечённому освещению. Полный исходный набор света из этих BSP не извлекается.

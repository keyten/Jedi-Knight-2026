# Исследование: отсечение перекрытых объектов (occlusion culling)

Не план реализации, а **план исследования**: сначала выяснить, сколько работы в кадре тратится на перекрытые
объекты, и только потом выбирать механизм. Объём исследования: 2–3 дня. Связано с
[rend2-gl43-review.md](rend2-gl43-review.md) (сравнение с внешним ревью, 2026-10-19).

## О чём речь

Сейчас Rend2 отбрасывает невидимое двумя способами:

- **PVS и areaportals** (предрасчитанная видимость BSP) — для мира и, через снимки сервера, для сущностей. PVS
  грубый: в помещениях работает хорошо, на открытых картах слабо, потому что из любой точки «видно» почти всё.
- **Отсечение по пирамиде вида** — боксы и сферы моделей и поверхностей (`R_CullLocalBox`, счётчики
  `c_box_cull_*` и `c_sphere_cull_*`).

Перекрытие — «модель целиком за стеной или холмом» — не проверяется никак, ни запросов видимости, ни Hi-Z. Модель
за стеной проходит весь путь:
- фронтэнд: `R_AddEntitySurfaces` (`tr_main.cpp`, около строки 2137), кости G2 (`G2_TransformGhoulBones`,
  `tr_ghoul2.cpp`), сборка и сортировка draw surf;
- бэкенд: depth prepass, основной проход, velocity-проход.

**Hi-Z occlusion culling.** Из буфера глубины строится пирамида, где каждый тексель хранит **самую дальнюю**
глубину своего блока. Бокс объекта проецируется на экран, берётся уровень пирамиды, где бокс занимает 2×2
текселя, и сравнивается: если ближайшая точка бокса дальше самой дальней глубины в этих текселях, объект целиком
перекрыт. Тест дешёвый, его можно делать в compute для тысяч объектов сразу.

## Что уже снижает выигрыш (почему это не очевидная победа)

1. **Depth prepass есть** (`r_depthPrepass 1` по умолчанию). Фрагменты перекрытого объекта в основном проходе
   отбрасываются ранним тестом глубины, а дорогой `lightall` для них не выполняется. Значит, на GPU отсечение
   экономит в основном вершинную работу (скиннинг G2, вершинная анимация MD3, ветер растений) и растеризацию в
   prepass, основном и velocity-проходах, но не освещение.
2. **Тени не выигрывают.** Объект за стеной для камеры может быть виден для источника света, поэтому теневые
   проходы перекрытием камеры не отсекаются.
3. **Сцены JA небольшие.** Персонажей десятки, а не тысячи. Модель персонажа — несколько тысяч треугольников.
   Часть статических моделей (`misc_model`) вкомпилирована в мир компилятором карт и уже отсекается PVS.
4. **Готовый Hi-Z не подходит.** `tr.screenHiZImage` (`tr_screenspace.cpp`) хранит **ближайшую** глубину: она нужна
   для трассировки SSR/SSGI. Для отсечения нужна **дальняя**, иначе тест неконсервативен. Кроме того, пирамида
   строится только при SSR/SSGI и уже после opaque-прохода. Нужна отдельная пирамида max-глубины сразу после
   prepass.
5. **CPU-выигрыш требует задержки.** Чтобы не считать кости и не собирать draw surf перекрытых моделей, CPU должен
   знать результат до сборки кадра, то есть брать результат прошлого кадра через асинхронное чтение. Объект,
   который только что вышел из-за угла, тогда может пропасть на кадр. Это лечится двухфазной схемой (ниже), но она
   сложнее.

Поэтому решать «по ощущению» нельзя: нужно измерить, есть ли что экономить.

## Вопросы исследования

1. Сколько GPU-времени уходит на непрозрачную геометрию **моделей** против мира в prepass, основном и
   velocity-проходах?
2. Какая доля треугольников моделей (и, отдельно, мировых поверхностей) за кадр рисуется **полностью
   перекрытой**?
3. Сколько CPU-времени уходит на перекрытые модели во фронтэнде: кости G2, сборка поверхностей?
4. На каких картах и в каких сценах это существенно: помещения, открытые карты, толпы NPC, катсцены SP?

## Шаги

### 1. Таймеры по категориям

- Бэкенд, `r_speeds 100`. В итерации по draw surf (`tr_backend.cpp`, цикл около строки 1390 для prepass и
  основной проход) разбить время по типу поверхности: мир (`SF_FACE` / `SF_GRID` / `SF_TRIANGLES` без сущности),
  G2 (`SF_MDX`), MD3/IQM, brush-модели, растения (`SF_PLANT…`), спрайты.
  - Таймер на каждую смену категории слишком мелкий, поэтому отладочный режим `r_speedsCategories 1` сортирует
    поверхности так, чтобы категории шли подряд. Сортировка меняет порядок, но только в отладке.
  - Вместо этого можно засечь два прогона кадра: `r_drawentities 0` и `1`.
- Фронтэнд: `steady_clock` вокруг `R_AddEntitySurfaces` по типу модели и вокруг `G2_TransformGhoulBones`; вывод
  командой `r_entityStats`.
- Счётчики треугольников по категориям для каждого прохода.

### 2. Сколько перекрыто: запросы видимости (только отладка)

Режим `r_occlusionStats 1` (cheat):
- После depth prepass главного вида для каждой сущности с моделью и для каждой мировой поверхности или группы
  поверхностей листа BSP нарисовать **бокс** с запросом `GL_ANY_SAMPLES_PASSED`. Запрос вызывается через
  `glBeginQuery` / `glEndQuery`, на GL 3.2 это `GL_SAMPLES_PASSED`. Тест глубины `LEQUAL`, без записи цвета и
  глубины.
- Результаты читать **без ожидания** через 2–3 кадра (`GL_QUERY_RESULT_AVAILABLE`), как это уже сделано для
  солнечного блика (`tr.sunFlareQuery`, `tr_backend.cpp`).
- Копить по категориям: число объектов, число треугольников, а для G2 — время костей у перекрытых объектов.
- Бокс консервативен: если он целиком перекрыт, перекрыта и модель. Боксы, пересекающие плоскость near, считать
  видимыми.
- Вывод раз в секунду: «G2: N сущностей, M трис, перекрыто X % трис; мир: …; CPU костей на перекрытые: … мс».

### 3. Сцены

| Сцена | Зачем |
|---|---|
| `t2_trip`, `kejim_base`, коридоры | хороший PVS: ожидаем малую долю перекрытого |
| `yavin1`, `yavin2`, `t3_hevil` | открытые карты, холмы, скалы: PVS слабый |
| MP или SP с 20–40 NPC за стенами (`npc spawn`, бот-матч) | толпа: вершинная работа и кости |
| катсцена SP | много персонажей, камера близко |

Intel UHD (основная цель, 57 мс на кадр в замерах с конфигом пользователя) и RTX 2060, 1080p. Скриптом со скрытым
окном (`rend2-game-launch-hidden`), с фиксированными позициями через `setviewpos`.

### 4. Решение по результатам

Оценка возможной экономии = доля перекрытого × стоимость категории.

| Результат | Что дальше |
|---|---|
| Экономия на GPU < 1 мс на Intel и на CPU < 0.5 мс во всех сценах | **закрыть тему**, записать замеры в обзор |
| Заметна только на GPU (вершинная работа моделей в prepass, основном, velocity) | **вариант A**: запросы видимости и `glBeginConditionalRender` (GL 3.0, работает и на 3.2). Бокс тестируется после prepass, а основной и velocity-проходы модели рисуются под условием `GL_QUERY_NO_WAIT`. CPU ничего не ждёт; дешевле всего в реализации |
| Перекрытых объектов много (сотни и больше), запросы по одному слишком дороги | **вариант B (GL 4.3)**: пирамида max-глубины после prepass, compute-тест всех боксов за один диспатч, затем `instanceCount = 0/1` в indirect-командах поверхностей моделей (`glDrawElementsIndirect`). Нужен тип indirect в `DrawItem`, как в плане 6 |
| Существенна CPU-часть (кости G2, сборка) | **вариант C**: результат прошлого кадра через асинхронное чтение и двухфазная схема. Сначала рисуются объекты, видимые в прошлом кадре, по ним строится Hi-Z, остальные тестируются и дорисовываются, если стали видимы. Исчезновений нет, но это самый сложный вариант: два прохода сборки draw surf |
| Перекрыто много **мира** на открытых картах | отдельный план для групп мировых поверхностей (по листам BSP) с тем же механизмом A или B |

Для каждого варианта отдельно учесть порталы и зеркала (свой вид — свой тест или без отсечения), skyportal,
viewmodel (`RF_DEPTHHACK`, никогда не отсекать), прозрачные модели (их нет в prepass: тест по prepass для них
корректен, но они сами не являются перекрывающими), отражения воды.

# Rend2 material derived-data cache

Two independent cvars control the cache. `r_materialDDCWorld 0` (default)
controls textures first registered while BSP surfaces are loaded.
`r_materialDDCObjects 1` (default) controls NPC, object and other textures
registered outside that BSP surface phase. A disabled category neither reads
nor writes disk records. Both categories store CPU-side derived results under
the current game's `cache/r2m/` directory:

- Prepared diffuse RGBA pixels together with an autogenerated normal map. The
  diffuse has already received the normal-generation brightness adjustment.
- Autogenerated `_aORMS` pixels and their mean/sigma metadata.

The records contain no `shader_t`, renderer pointers, or GPU objects. Authored
normal maps, HDR images, and arbitrary images keep their existing load path.
GPU upload still occurs on every renderer initialization.

Each key includes the cache format version, operation, image name, flags,
source bytes from the virtual filesystem, and (for normal generation) candidate
authored `_n` sources. Both the record header and pixel payload are checked on
read. A missing, truncated, or corrupt record is recomputed. The format version
must change whenever the preparation algorithms or binary layout change.

With `r_loadProfile 1`, the `material DDC` line reports hits, misses, invalid
records, writes, and time spent hashing sources and reading/writing records.
Compare a first map load with a second load of the same map. Use
`r_materialDDCWorld 0` and `r_materialDDCObjects 0` for an A/B run; restart
the renderer between changes to avoid
in-memory image hits. These numbers alone do not measure end-to-end savings:
compare the enclosing map load and image/normal/auto roughness timings too.

Current scope is deliberately limited to the expensive generated material data.
Records are raw RGBA, so disk space and cold-load writes can be substantial.
There is no eviction yet; deleting `cache/r2m/` clears the cache safely. Records
created by v3 for world textures remain on disk even with the new world flag off.
Writes are direct, with validation on the next read rather than an atomic rename,
because the renderer import API does not expose a filesystem rename operation.
